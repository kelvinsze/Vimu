# 投屏兼容性与两秒重播诊断

## 目前确认的实测现象

- 爱奇艺未发现 Mivu；腾讯视频能够播放，但发现慢。
- Bilibili 发现顺畅，但车机的画面和声音确实重复，并非只在发送端进度条归零。
- 用户提供的 23:02:22–23:02:34 截图只有周期性的 GetPositionInfo / GetTransportInfo，没有可见的重复 SetAVTransportURI 或 Seek。
- 上述截图不包含 SOAP 返回值、AVPlayer 时间与内部跳转，尚不能据此确认重播根因。

## 本轮修改范围

1. 三个 SCPD 补齐已实现动作的参数、关联状态变量和数据类型。设备描述明确提供空 eventSubURL；当前仍不提供 GENA 事件订阅，不伪造成功的订阅接口。
2. SSDP 回复按控制端地址与实际路由选择 LOCATION，不再统一使用优先 Wi-Fi / 蜂窝地址。相同地址的各发现路径使用同一个 description.xml URL，去掉变化的 via 查询参数。
3. 为每个局域网 IPv4 接口发送对应地址的组播宣告，保留本机回环、地址单播及主要网络的 NW / 广播补充路径；宣告覆盖全部六个设备和服务目标。
4. 网络接口变化时重新加入组播并宣告。搜索回复与 SCPD 访问写入诊断历史。
5. 添加临时 `[DEBUG-cast]` 播放日志，不改变加载、跳转、状态回报或 CarPlay 呈现行为。

设备描述要求参考 [UPnP Device Architecture](https://upnp.org/specs/arch/UPnPDA10_20000613.htm)。完整的 AVTransport / DLNA 事件兼容性不在本轮完成范围内。

## 下一次实机复现

安装包含本轮修改的版本后：

1. 打开 Mivu，再用 Bilibili 投屏，等真实重播发生两三次。
2. 返回 Diagnostics，点击“复制完整诊断日志”，将文本发回。不要只截屏；完整日志同时保留发现和播放诊断。
3. 爱奇艺与腾讯分别测试一次，并注明 App、是否同一台手机、Wi-Fi 是否开启和大致发现等待时间。

日志以发生时间保存，最多保留 400 条；“仅显示播放诊断”不影响完整复制。播放诊断不记录签名 URL、Cookie 或鉴权头。

## 关键证据

- `LOAD` / `REPLACE_ITEM`：是否替换媒体；g 为加载代数，sameURL 只比较地址是否相同。
- `SEEK` / `SEEK_COMPLETED`：跳转来源、目标、是否完成。
- `TIME_BACKWARD` / `TIME_JUMP`：AVPlayer 自身的播放时间是否回退。
- `TICK`：真实播放时间、上次回报位置、时长、状态和速率；若画面重复但时间持续增长，应进一步检查媒体流内容。
- `CARPLAY`：是否在异常发生前重建播放配置或根页面。
- `STREAM_ERROR` / `FAILED_TO_END`：取流或播放错误代码。
- `SOAP ... response`：发送端实际查询到的状态和进度。

## 验证边界

描述契约检查对修改前实际源码报告 22 项缺项，修改后通过；本机 Swift 检查还覆盖回环、同机 LAN、多网卡回连地址、稳定 URL 与六项搜索响应。iOS XCTest 已增加对应回归检查。

这些检查不等于 iOS 构建、App 发现恢复或车机重播修复。未执行 Xcode 构建、安装或实车验收。临时日志需在根因确认后移除。
